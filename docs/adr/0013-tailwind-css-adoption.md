# ADR-0013: スタイリングにTailwind CSS v4を採用する

## ステータス

承認済み

## コンテキスト

フロントエンドの全画面がCSSなし・インラインスタイルのみのプレーンHTML状態にある。ポートフォリオとして公開するにあたり、見た目の完成度はUI/UXへの配慮を示す重要な指標となる。

スタイリング手法の選択肢を比較検討し、採用方針を決定する必要があった。

## 決定

Tailwind CSS v4（Viteプラグイン統合）を採用する。`@tailwindcss/vite` でViteに組み込み、CSS-first設定（`@import "tailwindcss"` + `@theme` ブロック）で運用する。

## 検討した代替案

| 案 | メリット | デメリット | 不採用の理由 |
|---|---|---|---|
| Tailwind CSS v4 | ユーティリティクラスで実装が速い。v4はViteプラグイン1つで設定完結。業界採用率が高くポートフォリオとしての訴求力がある | クラス列が長くなり可読性が落ちる場合がある | — (採用案) |
| CSS Modules | コンポーネントスコープが保証される。TypeScript型補完もある | ファイルが増えてディレクトリが煩雑になる。ユーティリティ的な使い方には向かない | セットアップコストに対してメリットが薄い |
| styled-components | コンポーネント内にスタイルを完結できる。動的スタイルが書きやすい | ランタイムコストがある。依存パッケージが増える。React 19対応が遅れがち | パフォーマンス面と依存増加がデメリット |
| vanilla CSS (global) | 依存ゼロ。ブラウザ標準のみ | クラス名の衝突管理が煩雑。大規模化すると保守コストが上がる | 書き始めが速い反面、一貫性の維持が難しい |

## 結果・影響

**得られるもの:**
- Viteプラグイン統合により設定ファイルが最小限（`vite.config.ts` への1行追加 + `index.css` への `@import` のみ）
- Tailwind v4のCSS-first設定で `@theme` ブロックによるカラーパレット定義が可能（収入=green、支出=red）
- ユーティリティクラスによりコンポーネント単位でスタイルが完結し、CSS Modulesのようなファイル分割が不要
- ビルド時に使用クラスのみを含む最小CSSが生成される

**犠牲にするもの:**
- JSX内にクラス名の列が増えて視覚的なノイズになる場合がある
- Tailwindの知識がないメンバーには読みにくい（ポートフォリオとしては個人開発のため問題なし）

**バージョン選定 (v4):**
v3はPostCSSベース・`tailwind.config.js` 必須の旧来設定だが、v4は `@tailwindcss/vite` プラグイン1つで統合でき、設定コードが大幅に削減される。将来的に見直す条件は特にない。
