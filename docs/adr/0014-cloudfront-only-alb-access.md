# ADR-0014: ALB へのアクセスを CloudFront 経由に限定し、IP 制限を AWS WAF へ移す

## ステータス

承認済み

## コンテキスト

[ADR-0008](./0008-private-network-nat-gateway.md) の決定3 で「アクセス制御は自宅IP(/32)のみ」と定め、ALB のセキュリティグループで `allowed_cidr` からのインバウンドだけを許可する構成にした。一方で [ADR-0011](./0011-client-side-routing-with-react-router.md) の SPA 配信に伴い、CloudFront に `/api/*` を ALB へ転送するビヘイビアを設けている。

この2つが両立しない。CloudFront から ALB へのオリジンリクエストは **CloudFront のエッジ IP** から発せられるため、自宅IP を許可した SG では**すべて遮断される**。実際にデプロイすれば API 呼び出しが全滅する構成になっていた。

回避策としてフロントエンドから ALB を直接呼ぶ案もあるが、こちらも成立しない。

- ALB のリスナーは HTTP:80 のみで ACM 証明書を持たない（独自ドメインが未取得のため）
- CloudFront は HTTPS で配信される。HTTPS のページから HTTP の API を呼ぶと**ブラウザが Mixed Content としてブロックする**

したがって「CloudFront 経由に一本化する」か「独自ドメインを取得して ALB を HTTPS 化する」かの二択になった。

なお CloudFront 経由に一本化すると、フロントエンドと API が同一オリジンになるという副次的な利点がある。CORS が発生せず、JWT を格納する Cookie（[ADR-0004](./0004-authentication-jwt-httponly-cookie.md)）も `SameSite=Strict` のまま扱える。

## 決定

CloudFront 経由のアクセスに一本化し、ALB は CloudFront 専用のオリジンとして扱う。具体的には次の4点を行う。

1. **ALB の SG インバウンドを、AWS マネージドプレフィックスリスト `com.amazonaws.global.cloudfront.origin-facing` からの HTTP:80 のみに変更する**（自宅IP の CIDR ルールは削除）
2. **CloudFront のカスタムオリジンヘッダー `X-Origin-Verify`（Terraform が `random_password` で生成）を ALB のリスナールールで検証し、一致しないリクエストには 403 を返す**
3. **IP 制限は CloudFront 側の AWS WAF（WebACL scope=CLOUDFRONT + IPSet）へ移設する。** ADR-0008 決定3 の「自宅IPのみ許可」という要件そのものは維持し、実施レイヤーだけを ALB の SG からエッジへ移す
4. **独自ドメインと ACM 証明書は導入しない。** CloudFront のデフォルト証明書のまま運用する

決定1と決定2は多層防御として組み合わせる。プレフィックスリストは「CloudFront を利用している全 AWS 顧客のエッジ」を許可するものであり、**これ単体では自分のディストリビューションに限定できない**ためである。カスタムオリジンヘッダーはビューワーが送信した同名ヘッダーを上書きするため、ブラウザからヘッダーを偽装して ALB に到達することはできない。

## 検討した代替案

| 案 | メリット | デメリット | 不採用の理由 |
|---|---|---|---|
| **採用案: CloudFront 経由に一本化 + プレフィックスリスト + オリジン検証ヘッダー + WAF** | フロントと API が同一オリジンになり CORS 不要・`SameSite=Strict` を維持できる。独自ドメインの取得が不要。ADR-0008 決定3 の要件を維持できる | WAF の月額 $6〜7 が増える。SG が 46 エントリを消費する | — |
| 代替案A: 独自ドメインを取得し ACM で ALB を HTTPS 化してフロントから直叩き | ALB の SG で自宅IP制限をそのまま維持できる。WAF が不要 | ドメイン費用（約$12/年）。クロスオリジンになるため Cookie を `SameSite=None` に変更するバックエンド改修と CORS 設定が必要。同一オリジンの利点を失う | ADR-0004 の Cookie 設定に手を入れる必要があり、変更範囲がインフラ外へ波及する。ドメイン未取得という前提も変わらない |
| 代替案B: WAF を導入せず CloudFront を全世界に公開する | 追加コストがゼロ。設定が最も単純 | アプリがインターネット全体から到達可能になる。保護はログイン認証のみ | ADR-0008 決定3 の「自宅IPのみ」を満たせない。要件の緩和には別途合意が必要 |
| 代替案C: ALB を internal にして CloudFront VPC Origin を使う | パブリックサブネットに ALB を置かずに済み、構成として最も筋が良い | 2024年末に追加された比較的新しい機能で、Terraform 側のサポートが未成熟 | 初回デプロイで扱う不確実性を増やしたくない。将来的な移行候補として残す |

## 結果・影響

**得られたもの**

- CloudFront 経由の API 呼び出しが機能するようになる（この修正なしでは全滅していた）
- フロントと API が同一オリジンになるため、CORS 設定が不要になり、`AllowedOrigins` を ECS タスクへ注入する必要もなくなった。加えて `frontend` モジュールの CloudFront ドメインを `ecs` モジュールへ渡さずに済むため、**モジュール間の循環参照を避けられる**
- ALB へ直接アクセスすると 403 が返るため、オリジンが露出しても素通しにならない

**犠牲にしたもの・コスト**

- **AWS WAF の費用が月 $6〜7 増える**（WebACL $5.00 + ルール $1.00 + リクエスト従量）。ADR-0008 で見積もった月額 約$90〜95 は **約$96〜101** に増える
- ALB の SG インバウンドがプレフィックスリストで **46 エントリ**を消費する。「セキュリティグループあたりのインバウンドルール数」のクォータは 60 なので残り 14。当面は足りるが、ALB SG にルールを増やす場合はクォータの引き上げが必要になる（2026-08-15 時点の実測値。AWS 側で随時更新されるため、増える可能性がある）
- オリジン検証シークレットが Terraform の state に保存される。state バケットは暗号化とパブリックアクセスブロックを設定済み

**ADR-0008 への影響**

決定2（SG は SG 間参照で連鎖）の ALB 部分と、決定3（アクセス制御は自宅IP のみ）の実施レイヤーが本 ADR で変わる。要件そのものは維持しているため置き換え（Superseded）ではなく追記（Amended）として扱う。

**将来見直す条件**

独自ドメインを取得した場合は、CloudFront に `aliases` と ACM 証明書を設定する。その時点で代替案A（ALB の HTTPS 化）や代替案C（CloudFront VPC Origin）を再検討する価値がある。ただし同一オリジン構成の利点は失いたくないため、ALB 直叩きへ戻す積極的な理由は現状ない。
